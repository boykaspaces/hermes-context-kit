# Project Adoption Specification v2

## Purpose

Define a runtime-neutral contract that lets an unfamiliar agent identify,
resume, validate, and safely evolve one project without conversation history
or assumptions about a particular agent product.

## Neutral namespace and adoption manifest

Every v2 project stores `.context-kit/manifest.json`. It records:

- `schema_version`: adoption-manifest schema version, currently `2`;
- `spec_version`: project protocol version, currently `2`;
- `kit_version`: immutable Context Kit release used for adoption;
- `profile`: `minimal`, `repository`, or `multi-repo`;
- `features`: explicitly enabled optional capabilities;
- `runtime_adapters`: zero or more explicit runtime adapter identities and
  versions;
- `workflow_adapter`: one optional proposal/acceptance adapter identity and
  version; and
- `extensions`: optional consumer-owned metadata that does not redefine core
  fields.

The `.context-kit/` name identifies this protocol, not an agent runtime.
Runtime-specific instruction entry points and installation paths are supplied
by adapters and are not core artifacts.

## Core ownership

| Artifact | Owns |
|---|---|
| `PROJECT.md` | Stable project ID, display name, goal, and lifecycle status |
| `.context-kit/manifest.json` | Adopted protocol/release/profile/features/adapters |
| `.context-kit/state.md` | Concise current project summary and primary focus |
| Runtime adapter artifact | Runtime-specific instructions and workspace binding |

Repository and multi-repository profiles add the routed artifacts defined by
their profile. No artifact may infer current state from timestamps, filename
order, branch naming, or conversation recency.

## Canonical state and proposals

The consumer declares one accepted integration ref through its workflow
adapter or repository policy. State reachable from that ref is canonical.

A proposal ref contains a candidate next state. It may include a Task
transition to `Completed`, updated indexes, accepted component revisions, and
validation evidence that will become canonical together. Those candidate
facts must be described as proposed when reporting from outside the accepted
ref. Merging or otherwise accepting the proposal activates the entire state
transition atomically.

Do not require the proposal to record its own acceptance as a prerequisite for
the state it contains. That is self-referential. The workflow system owns the
acceptance event; optional read-only verification may confirm it afterward
without creating another proposal. A new proposal is required only when the
accepted outcome differs from the candidate facts, such as a rewritten
component revision that invalidates a lock.

## Profiles

### minimal

Requires project identity, adoption metadata, and current state. It does not
require an agent-specific instruction file.

### repository

Adds the context index, Task index/current pointer, and decision index.
Checkpoints and memory remain opt-in.

### multi-repo

Adds repository context plus System Task routing and an immutable component
graph. Detailed state and evidence semantics are owned by the
multi-repository specification.

## Runtime adapters

An adapter maps core concepts to one runtime without redefining them. It may
provide instruction templates, workspace binding rules, Skill installation
guidance, and runtime-specific validation. Projects may declare more than one
adapter. Absence of an adapter is valid for CLI-only or manually integrated
projects.

## Compatibility

Project specification v1 uses `.hermes/context-kit.json` and `.hermes/` state
paths. A v2 implementation treats those paths only as explicit legacy input.
Migration is dry-run first, preserves project content, writes the v2 namespace,
and does not silently delete legacy artifacts. After review, the consumer
removes legacy duplicates in the same accepted proposal that establishes v2 as
canonical.
