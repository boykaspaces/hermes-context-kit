# Project Adoption Specification v1

## Purpose

Define the smallest durable contract that lets an unfamiliar agent identify,
resume, validate, and safely evolve one project without conversation history.

## Adoption manifest

Every adopted project stores `.hermes/context-kit.json`. It records:

- `schema_version`: adoption-manifest schema version, currently `1`;
- `spec_version`: project protocol version, currently `1`;
- `kit_version`: immutable Context Kit release used for adoption;
- `profile`: `minimal`, `repository`, or `multi-repo`;
- `features`: explicitly enabled optional capabilities;
- `extensions`: optional consumer-owned metadata that does not redefine core
  fields.

The manifest identifies the contract; it does not copy current project state.

## Core ownership

| Artifact | Owns |
|---|---|
| `PROJECT.md` | Stable project ID, display name, goal, and lifecycle status |
| `AGENTS.md` | Repository-local operating and validation instructions |
| `.hermes/context-kit.json` | Adopted protocol/release/profile/features |
| `.hermes/state.md` | Concise current project summary and primary focus |

No artifact may infer current state from timestamps, filename order, Git ref
names, or conversation recency.

## Profiles

### minimal

Requires only the four core artifacts. Use it for a new or small project that
does not yet need persistent Task or decision navigation.

### repository

Adds the project context index, Task index/current pointer, and decision index.
Checkpoints and memory remain opt-in features.

### multi-repo

Adds repository-profile context plus System Task routing and an immutable
component lock. Detailed state and evidence semantics are owned by the
multi-repository specification.

Profiles are monotonic: a broader profile includes the required behavior of
the profiles below it. A project may upgrade its profile through a migration;
downgrading must first prove that no removed capability owns live state.

## Active work and user attention

Task lifecycle status and attention are distinct. `Status: In Progress` may
carry `Attention: User Action Required` when independent work can continue.
Use `Status: Blocked` only when the Task cannot progress.

When user action blocks a state transition, record `Waiting On`,
`Required Action`, and the evidence needed to resume. Recovery and status
reporting surface that action before unrelated next steps. The fields are
cleared only after the blocker is explicitly confirmed or revalidated.

## Evolution

An upgrade begins with a read-only audit. Mutation requires an explicit target
version and user authorization. The migration preserves project-owned content,
reports unsupported extensions, validates the result, and retains a recoverable
backup or Git diff until acceptance.
