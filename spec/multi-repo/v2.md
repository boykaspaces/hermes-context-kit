# Multi-Repository Coordination Specification v2

## Purpose

Coordinate immutable component revisions without treating source delivery,
integration acceptance, and production deployment as one state.

## Component state

Each component records:

- source identity: repository, URL, branch, optional Component Task, and exact
  revision;
- `source_state`: `pending`, `handoff-ready`, or `merged`;
- `acceptance_state`: `pending`, `locked`, or `verified`;
- deployment applicability and state;
- optional consumer extensions.

A non-pending source or acceptance state requires a full lowercase
40-character commit SHA. `acceptance_state: locked` or later requires exact
equality with the component lock.

The canonical `components/lock.json` records `name`, `repository_url`, and
`source_revision` for every accepted component. This is the portable minimum
needed to fetch and reproduce an immutable graph. Local checkout paths,
deployment bindings, and live status are consumer-owned state and do not
belong in the lock.

## Deployment applicability

Deployment is a separate object:

| Applicability | Allowed state |
|---|---|
| `required` | `pending` or `deployed` |
| `not-applicable` | `not-applicable` |

Governance, build-time, documentation, or protocol components may be accepted
without being falsely described as deployed. A required component reaches
`deployed` only with stable evidence.

## Integration state

The integration object separately records:

- `verification_state`: `pending` or `verified`;
- `deployment_state`: `pending`, `deployed`, or `not-applicable`;
- validation evidence;
- deployment evidence;
- rollback evidence when deployment is required.

Verified integration requires every included component to be at least locked
and requires validation evidence. Deployed integration requires every
deployment-required component to be deployed, deployment evidence, and a
rollback pointer. Components marked not applicable do not block deployment.

## Evidence

Evidence entries are objects:

```json
{
  "ref": "evidence/TASK-014-validation.md",
  "summary": "Exact locked revisions passed clean-room validation"
}
```

`ref` is the auditable claim source and must be an HTTP(S) URL or a
repository-relative regular file. `summary` is optional human context and does
not independently advance state.

## Access boundaries

A validator reports component checks as `passed`, `failed`, or `not_checked`.
Inaccessibility never becomes evidence of success and does not authorize
mutation in the inaccessible repository. The integration owner may retain a
pending state, request a Handoff, or perform acceptance after access becomes
available.

## Proposal ordering and activation

When delivery uses change proposals, accept Component proposals first. Keep the
System proposal open while recording the resulting exact revisions, component
lock, integration evidence, and completed System Task candidate state. Accept
the System proposal last; that event activates the complete candidate state on
the integration project's canonical ref.

The System proposal must not require evidence of its own acceptance inside the
state it carries. Optional post-acceptance verification is read-only unless the
accepted outcome differs from the candidate facts. A rewritten Component SHA
must be reconciled before the System proposal is accepted.

## Compatibility

The previous `delivery_state`/`integration.state` manifest is schema v1.
Consumers migrate explicitly to v2; validators may read v1 for compatibility
but must not silently reinterpret v1 values as the separated v2 states.
